# 0014. Code folding: anchored folds, hidden lines in the wrap layer

- Status: Accepted
- Date: 2026-10-03

## Context

M7 adds folding. [ADR 0004](0004-display-map.md) reserved a `FoldMap` layer under the wrap layer so that folding would not touch rendering, hit-testing or scrolling, and [ADR 0006](0006-anchored-decorations.md) said folds should reuse anchors. What was left open: what a fold hides, how it composes with wrap, how fold ranges are found, and what the cursor does at a fold.

## Decision

- **A fold hides whole lines after a header line.** The header keeps all of its (wrapped) rows, a placeholder chip follows its text, and the line holding the closing token (`}`, `</div>`, a code fence) stays visible. A collapsed `{ ⋯ }` row that joins the header and the closing line was considered and left out: it needs rows made of pieces of two buffer lines, which `DisplayRow`, the layout cache, hit-testing and highlighting would all have to learn. The model (hidden whole lines) does not rule it out later.
- **Folds are pairs of anchors** in the document's `AnchorSet`: the start at the end of the header line, the end at the end of the last hidden line, both with left gravity. Typing at the end of a header, or a line break there, therefore leaves the header where it is (a new line becomes part of the fold, and the cursor entering it opens the fold). A fold whose body is deleted is dropped; two folds never share a header; folds nest.
- **`FoldMap` keeps the line numbers, derived.** Next to the anchors it holds each fold's header and last line, and the hidden lines as merged intervals with running totals, so buffer line ↔ fold line and `isHidden` are binary searches. An edit that adds or removes no line break cannot move any fold from a line to another and costs nothing. One that does costs O(folds) integer work (shift the later folds, re-read the anchors of the ones the edit touched). A hidden line maps to the fold line of its visible header, so every position in hidden text resolves to the end of the header (`DisplayMap::visiblePosition`).
- **Wrap composes through a hidden bit.** The `WrapMap` stays indexed by buffer line and keeps a line's row count when it is hidden, but a hidden line contributes zero rows to every sum, so `lineAtRow` and `firstRowOfLine` skip it and unfolding needs no re-wrap. The `DisplayMap` mirrors the fold layer into those bits when folds change (only over the lines that changed) and when wrap is switched on. ADR 0004's picture of stacked layers stays true for the no-wrap path; with wrap the fold layer is a flag inside the wrap layer, because wrapping is keyed by buffer line and refined in the background. The background worker wraps hidden estimated lines too, which is wasted work but keeps the bookkeeping simple.
- **Fold ranges come from a `FoldProvider`.** `foldRanges(snapshot, firstLine, lastLine)` answers for the headers in a line range; the gutter asks for the rows in its plan. Two providers ship. `IndentFoldProvider` (the default) makes every line followed by deeper lines a header and ends the range before the next line at the header's level, ignoring blank lines; it reads the rope in one sweep, answers in 256-line blocks cached per document version, and does not offer a range whose end is more than `maxScanLines` (20,000) past the requested lines, because finding it would cost every scroll step a long scan (fold all has no limit). `TreeSitterFoldProvider` runs `folds.scm` captures (`@fold`, `@fold.keep_last`) over the highlighter's tree and its injected layers, trims the end line with `foldEndLine` (a node that ends at column 0 ends on the line before; a last line holding only a closing token stays visible), and falls back to the indent provider where the tree does not reach: no queries for the language, no tree yet, or outside a windowed parse of a big file. No pinned grammar ships a `folds.scm`, so the queries live in `src/syntax/queries/`.
- **Cursor semantics.** Movement steps over folded lines by default (`SkipFolds`): character, word and document-end moves that would land in hidden text go to the start of the next visible line, or back to the end of the header; row moves already work in rows. With `UnfoldOnEnter` movement may enter a fold and the editor opens it. Either way, an empty selection that ends up in hidden text for any other reason (`setCursorPosition`, undo, an edit that joined lines) opens the folds that hide it; a non-empty selection is left alone, so select-all does not unfold. Folding with the cursor inside the new fold moves the cursor to the end of the header. A line unit (triple-click, gutter line selection) on a folded header takes its hidden lines along.
- **Rendering.** The chip is two rectangle batches in the backdrop (a pill and three dots), placed after the header's last row; a press on it unfolds. The fold column draws one cached chevron image per state on the first row of each header. `GutterColumn::hoverLine` tells a column which line the pointer is over; the fold column shades the rows of the hovered region. Relative line numbers count visible lines.
- **Commands.** `foldAtCursor` folds the innermost region around the cursor that is still open (so repeating it works outwards), `foldAll`, `unfoldAll`, `foldToLevel(n)` (replaces the folds with those of nesting level n), `toggleFold(line)`. They are plain functions over the `DisplayMap` and a provider in `core/folding.h`; the editor adds cursor handling. Keys: Ctrl+Shift+[ and ] at the cursor, Ctrl+Alt+[ and ] for all.

## Consequences

- Measured (release, 2M-line nested-block text, `benchmarks/results/2026-10-03-folding.json`): ranges for the whole text 41 ms; for a viewport, cold, 0.66 ms; fold all (666k ranges, 1.3M anchors) 166 ms, unfold all 80 ms; toggling one fold with 100k present 62 µs (73 µs with wrap); a keystroke inside a line with 100k folds 6 µs (23 µs with wrap); a line break with 100k folds 121 µs (140 µs with wrap); a row query 0.9 µs (2.5 µs with wrap). Fold all misses the 50 ms the plan hoped for; the cost is creating the anchors. Scrolling a 100 MB file with the gutter and 20,000 folds (`2026-10-03-folding-scroll-folds.json` against `-baseline.json`, same session): smooth and fling frame intervals stay at the 8.3 ms display period, polish (0.40 ms smooth, 0.85 vs 0.93 ms fling) and sync are within run-to-run noise of the no-fold runs. Random jumps vary more between runs than between the two variants (dropped frames 0.7–4% without folds, 15% with in one run, where the refresh period also differed), so no cost is claimed or ruled out there.
- Markers, change bars and bookmarks on hidden lines are not drawn; a marker on a folded header shows because it is on the header. Showing a fold's markers on its header is a later refinement.
- Delete at the end of a folded header joins the first hidden line to the header and leaves the fold closed over the rest; Backspace at the start of the line below a fold joins it to the last hidden line, which opens the fold (the cursor is in it). Neither unfolds first, as some editors do.
- Folds are not stored in the document or restored after a reload; a host can read `displayMap().folds().folds()` and give them back with `setFolds`.
- A fold provider asked for many lines at once (fold all) on a huge tree-sitter document without a full tree gets indentation ranges for the part outside the window.
- Not done: collapsed `{ ⋯ }` rendering, folding by selection, a fold-level key chord, persistence, hands-on mouse checks in a real window (tests use synthetic events).
