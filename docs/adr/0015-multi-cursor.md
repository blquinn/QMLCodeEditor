# 0015. Multi-cursor: reused anchors, grouped edits that coalesce, culled overlays

- Status: Accepted
- Date: 2026-10-03

## Context

[ADR 0005](0005-commands-and-selections.md) and [ADR 0010](0010-command-layer.md) built the command layer around an always-present `SelectionSet`, so M8 was mostly about making the set cheap at ten thousand entries and about the gestures that create many selections. Open items from ADR 0010: `set()` recreated every anchor, the overlay build walked every selection each frame, and a multi-selection edit was never merged into a typing run.

## Decision

- **`SelectionSet::set()` moves anchors instead of recreating them.** `AnchorSet::move(id, offset)` keeps the id and gravity, updates in place when the neighbours still bound the new offset, and otherwise erases and re-inserts. `set()` reuses entry *i* for selection *i*, creating or removing only the difference in count, and skips anchors that are already where they should go. Typing at N cursors therefore costs no anchor allocation: right-gravity anchors already sit at the new cursors. An already ordered, disjoint list skips the sort and merge.
- **Edits made by anyone can pull selections together.** Removing text collapses anchors, so two selections can end up touching. The set flags this when a change removes text and, when the batch ends, scans once (O(n)) and merges what overlaps, the primary following its merge. Nothing else needs a scan: insertions cannot make selections touch.
- **Lookup is a binary search.** Selections are sorted and disjoint, so `lowerBound(offset)` / `indexAt(offset)` search the entries by anchor offsets. `add()` inserts one selection at its place without touching the others (it falls back to `set()` when the new one overlaps a neighbour). Ctrl+click, add-next-occurrence and the overlay build use these.
- **A group of typing or deleting edits coalesces like a single edit does.** `endEditGroup(after, kind)` merges the group into the top undo step when that step is unsealed, of the same kind, within the timeout, free of line breaks, and when the group starts from exactly the selections that step ended with. Undo replays the recorded edits in reverse, so the merge needs no position arithmetic. Typing "abc" at 10,000 cursors is one undo step. Enter, indent, paste and word deletion stay a step each. Moving the cursors ends a run.
- **Creating selections.** Ctrl+Alt+Up/Down (`addCursorVertical`) adds a cursor one display row above the topmost or below the bottom-most selection, keeping the goal x, so wrap and folds are respected and short lines don't lose the column. Ctrl+click adds a cursor, or removes the one under the click; Ctrl+drag adds a selection (the drag replaces only its own selection in the list it started from). Escape collapses to the primary. Ctrl+D selects the word under empty cursors, then adds the next occurrence after the primary, wrapping, skipping text that is already selected (a touching match counts as selected, because touching selections merge); it matches whole words when the selected text is a whole word, otherwise substrings. Ctrl+Shift+L selects all occurrences up to `maxSelections` (100,000 by default; every selection is two anchors) and reports the cap.
- **Search runs over rope chunks.** `core/textsearch` walks `ChunkIterator`, carries `needle.size() - 1` units across chunk boundaries and uses `QStringMatcher`. No whole-document string is built. The scan runs at about 2.5 G units/s on the 100 MB file (a miss takes 40 ms).
- **Box selection** is one selection per display row between the anchor and head rows, from the offset nearest the anchor x to the one nearest the head x (`CursorLayout`), so tabs, wide characters, wrapped rows and folds behave as the cursor does. Rows too short for the box get an empty selection clamped to their end instead of being skipped, so typing lands on every row (VS Code's behaviour). Alt+drag and Shift+Alt+drag start it (window managers often keep plain Alt+drag); x is kept in content coordinates so auto-scroll doesn't skew the box.
- **Clipboard.** With more than one selection every selection contributes a piece (empty ones too), joined by line breaks for the text flavour, and the pieces also travel as JSON in `application/x-qce-pieces` so pieces with line breaks of their own survive. Paste with as many selections as pieces (from that flavour, else the lines of the text, ignoring one final break) gives each its piece; any other count gives everyone the whole text. Large copies (over 1 M units) keep the worker path and the plain-text flavour only.
- **Overlays are culled by search, not by count.** `buildOverlays()` finds the first selection that can show with `lowerBound` and stops at the first starting after the plan (extended past hidden folded lines), and drops cursors and selections wholly outside the horizontal viewport. The cost is O(log n + visible) whatever the number of selections, and the number of rectangle nodes is bounded by the viewport, so the single-geometry batch considered for MULTI-06 was not needed: the existing one-node-per-rectangle batches stay.

## Consequences

- Measured on the 100 MB file (release, `benchmarks/results/2026-10-03-multicursor-*.json`): typing one character at 1,000 cursors takes 5.6 ms from key to frame (3.5 ms handling), at 10,000 cursors 27 ms (24 ms handling, roughly 2.4 µs per edit: rope edit, three position lookups, anchor update and the display-map update). One undo reverts it. Scrolling at 120 fps is unchanged with 10,000 cursors alive (8.3 ms frame interval). `set()` with 10,000 same-sized selections takes 9-17 ms, and `findAll` over 100 MB capped at 100,000 matches takes 30-45 ms.
- 10,000 cursors is interactive but not inside the 8 ms keystroke target. The per-edit cost is spent in `TextDocument::apply` and its listeners (one `changed` signal per replacement); coalescing the notifications of an edit group into one would be the next step if this needs to go lower.
- The software scene-graph backend (used by the offscreen tests) did not paint a rectangle node created in the same sync in which the scroll offset moved; it paints it after the next change. The tests work around it. It does not occur with the GPU backends.
- Touching selections always merge, so adjacent matches of Ctrl+Shift+L (`abab` for `ab`) become one selection.
