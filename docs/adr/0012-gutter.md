# 0012. Gutter inside the editor: columns paint into the frame plan

- Status: Accepted
- Date: 2026-10-02

## Context

M5 adds line numbers, a change column and host-supplied columns to the left of the text. The gutter has to scroll in lock step with the text, know which rows are continuation rows of a wrapped line ([ADR 0011](0011-soft-wrap.md)), keep a stable width while scrolling, and cost almost nothing per frame on a 100 MB file ([ADR 0009](0009-rendering-pipeline.md)). Hosts also want to put their own things in it (breakpoints, git bars, bookmarks) without writing C++.

## Decision

- **The gutter is part of `CodeEditor`.** The editor reserves `gutterWidth` on its left and everything text-related uses `textViewportWidth()` (`width - gutterWidth`): viewport wrap, horizontal clamping, the current-line band, hit-testing (`positionAt`, `rectForPosition`) and the input-method rectangle. A separate gutter item bound to an editor would have to rediscover the visible rows and would sync a frame apart from the text; this way both are built in the same `updatePolish` from the same plan and drawn from the same origin row.
- **Columns paint into the frame plan.** A `GutterColumn` (a `QObject`, so QML can declare them in `CodeEditor.gutterColumns`) reports a width and, for the rows of the plan, emits rectangles, text labels and images through a `GutterPainter`. `FramePlanRow` now carries its `DisplayRow`, so a column sees `line`, `rowInLine` and `isFirst()` without asking the display map again. The scene turns the result into a gutter subtree next to the text subtree: its own clip, a y-only scroll transform sharing `m_originRow`, a colored-rectangle batch, a pooled row of text nodes for labels (the same pooling as text rows) and an image batch. Scrolling inside the layout window still rewrites matrices only.
- **Width is a function of the document, not of the view.** `LineNumberColumn` sizes itself from the digit count of `lineCount` (at least `minimumDigits`, plus a cell of padding either side), so it changes when the line count crosses a power of ten and never while scrolling. Columns are measured at the start of each full polish, before wrap is applied, because the gutter width is an input to the wrap width. A change marks the wrap dirty and re-anchors the view like a resize does.
- **Labels are cached by number.** Line-number labels are `QTextLayout`s in a small map keyed by the number; relative mode reuses the same few dozen. Color (current line or not) is applied to the text node, not baked into the layout, so moving the cursor re-fills nodes but lays nothing out.
- **Markers are anchored line ranges.** `LineMarkerSet` (core) holds markers as a pair of anchors ([ADR 0006](0006-anchored-decorations.md)): the start anchor has right gravity at the start of the first line and the end anchor left gravity at the end of the last line. A line break typed at the start of a marked line therefore pushes the marker down with its line, and one typed at the end of the last line does not stretch it. Queries are a binary search on the start offset plus a bounded walk back (`maxSpan`, an upper bound that grows by what edits insert and is recomputed after enough drift). `MarkerColumn` is the host API on top of it (bars over every row of a line, icons on the first row only, priorities); a text reset removes the markers, because the lines they referred to are gone.
- **Change tracking has no diff.** `ChangeColumn` marks `[startLine, newEndLine]` as modified on every edit, merging neighbours with `markRange`, and a notch where whole lines were removed. It ignores edits made while a file is loading and clears on reset, load and save. Undoing back to the saved text leaves the marks until the next save; a host with a real diff drives a `MarkerColumn` instead.
- **QML columns are delegates on a holder.** `DelegateColumn` instantiates its `delegate` for the rows in the plan, first rows only by default, and passes `line`, `row`, `rowInLine`, `firstRow` and `current` as required properties. Items are children of one holder item whose y carries the scroll offset (`origin * lineHeight - contentY`); item y values are relative to an origin row that is re-based beyond 2048 rows, like the scene's matrices. On the scroll fast path the editor only calls `scrolled()`, which moves the holder. Rows that leave the plan hand their item to rows that enter; at most 64 spares are kept. Delegates exist only for the plan (visible rows plus half a viewport each side).
- **Interaction.** A press left of `gutterWidth` goes to the column under the pointer: its `clicked(line, button, modifiers)` fires, and if the column `selectsLines` (line numbers do) the press starts a drag by whole lines through the same machinery as a triple-click, with shift extending from the selection's anchor. Delegates with their own `MouseArea` receive events before the editor because they are its children. The pointer is an arrow over the gutter.
- **No gutter by default.** `gutterColumns` is empty unless set, and with no columns every path is as it was: no extra nodes, no width.

## Consequences

- Measured on a 100 MB, 2M-line file (release, Wayland, `benchmarks/results/2026-10-02-gutter.json`): smooth scrolling with line numbers, change and marker columns keeps 8.3 ms frame intervals and creates no nodes in steady state; polish rises by about 20 µs a frame (311 → 331 µs mean) and sync by about 30 µs. With wrap at the viewport polish is 397 µs. Random jumps, where every layout and label is cold, cost about 0.5 ms more polish (2.07 → 2.57 ms mean) and the share of frames over 1.5 display intervals goes from 5.8% to 10.5% with absolute numbers (7.7% relative; run to run noise is a few percent).
- Moving the cursor in relative mode renumbers every visible row: sync mean rises from 0.08 ms to 0.59 ms (each label's text node is re-filled) while frame intervals stay at the display rate. Absolute mode refills only the two rows whose highlight changed (0.14 ms).
- A column's width is part of wrap, so changing it re-wraps in viewport mode; that is the resize path and costs the same.
- Hit-testing and scrolling code outside `CodeEditor` that assumed the text starts at x = 0 must add `gutterWidth`. `rectForPosition` and `positionAt` already do.
- `MarkerColumn` and `ChangeColumn` each own a `LineMarkerSet`, and every one of them listens to every edit. That is fine for a few columns; a decoration system with many layers (M9) should share one structure.
- Not done: horizontal auto-scroll of a drag that started in the gutter, bookmarks that follow edits in the demo (the demo keeps line numbers), and fold markers in the gutter (FOLD-04 adds a column through this API).
