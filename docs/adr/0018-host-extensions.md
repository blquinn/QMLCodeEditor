# 0018. Host extensions: registered languages, token styles and highlight overlays

- Status: Accepted
- Date: 2026-10-07

## Context

Repose, a host application that takes the library through CPM, needs a tree-sitter language of its own (GraphQL) and `{{variable}}` highlighting. It could do neither without editing the library: the language list was a private, hard-coded table; `TokenStyle` was a fixed enum, so the host borrowed `Link` and `Heading` (restyling real Markdown headings); and the only way to draw over the syntax highlighter's output was to wrap it, forwarding `attach`, `detach` and `invalidated`, cutting its spans around each match and sorting them again.

[ADR 0013](0013-tree-sitter-highlighting.md) fixed how highlighting works and [ADR 0016](0016-decorations-and-diagnostics.md) how decorations work. This one adds three small public extension points that sit on top of both and change neither.

## Decision

### Language registration (API-12)

- **`LanguageRegistry::registerLanguage(LanguageInfo, QString *error)`** adds a language or replaces the one with the same id. The id, extensions, file names, interpreters and aliases are lower-cased (a leading dot on an extension is dropped). A language with no id, no grammar or a grammar outside the ABI range of the vendored runtime is rejected with a reason. Built-ins can be overridden, nothing can be removed. New languages are tried before the built-ins in `detect()`, so a host's mapping of an extension wins.
- **Queries come as files or as text.** `highlightQueries`/`injectionQueries`/`foldQueries` take paths: relative ones are the library's own resources, ones starting with `:` or `/` are read as they are (a host's Qt resource or a file). `highlightSource`/`injectionSource`/`foldSource` are appended after the files, for hosts that don't ship queries as resources. A pattern that does not compile against the grammar is dropped and reported in `CompiledLanguage::warnings`, as for built-ins.
- **Registration is for startup, and the registry is read without locks.** The parse workers read the language list (injections look languages up) while the GUI thread may be parsing, so growing the list while any editor has a parse in flight would be a data race. Rather than put a lock on every `find()` and `detect()` (on the path of every language change and every injection), the contract is: register on the GUI thread before editors get text (a debug assertion checks the thread). What is synchronized is the one thing workers write, the cache of compiled queries (`compiled()`, one mutex, unchanged). A copy-on-write list would lift the restriction at the cost of a shared pointer per lookup; nothing needs that yet.
- **Entries have stable addresses** (`std::deque`, added at the front): `CompiledLanguage::info` and the highlighters point at them. A replaced language is overwritten in place and its cached compile is dropped; whoever still holds the old `CompiledLanguage` keeps working with it. Editors pick the new definition up when their language is resolved again, which a `SyntaxHighlighter` does on every `language` or `fileName` change, so a language registered after an editor exists applies from the next change. Compilation stays lazy: a registered language nobody uses costs a list entry.
- **Headers.** tree-sitter's `api.h` already reaches hosts through `qce_grammars`; a host compiles its grammar's `parser.c` itself and passes the `tree_sitter_<name>` function. No install rules were added: hosts consume the library with `add_subdirectory` or CPM, which see `src/` already.

### Host-defined token styles (API-13)

- **`TokenStyle` has room for 192 host styles** (values 64 to 255; the built-ins stay below 20, so nothing changes for them). `registerTokenStyle(name)` is idempotent, case-insensitive, thread-safe and permanent; a built-in name returns the built-in style, and the call returns `Default` when the slots are used up. Names can have dots (`variable.defined`). `tokenStyleName()` now returns a `QString` because custom names are not literals.
- **Queries reach them by capture name.** `styleForCapture` looks for a registered style at every step of its longest-prefix walk, ahead of the built-in table, so `@graphql.directive` in a host query is that style, and `@graphql.directive.deprecated` falls back to it. A query's capture styles are fixed when the language compiles, so a host registers its styles before its languages (re-registering the language picks up later ones).
- **Theme colors them by name** through the same `tokenStyles` map (`color`, `bold`, `italic`, and now `background`), or in one call with `Theme::setTokenStyle(name, color, background, bold, italic)`, which registers the name and emits `changed()` once. The theme keeps 256 formats indexed by style value; styles registered after the last rebuild are covered the first time a layout asks for them.
- **Backgrounds are drawn by the editor, not by the text node.** `QSGTextNode` is not relied on to paint format backgrounds. `layoutForRow` collects the stretches of a row whose style has a background into `LineLayout::styleBackgrounds` (row columns, merged when adjacent and equal), and `buildDecorations` turns them into spans of the same backdrop batch as Background decorations, so they sit under the selection and the text and behave with wrap, folds and injected hints. A flag on the theme means nothing is looked up when no style has a background.

### Highlight overlays (API-14)

- **An overlay is a `Highlighter`**, listed in `CodeEditor::overlays` (a `QQmlListProperty<qce::Highlighter>`, so QML bindings stay typed and compile) or added with `addOverlay`. The editor attaches and detaches it like the main highlighter, forwards its `invalidated` to the same targeted layout drop, and forgets it when it is destroyed.
- **The editor does the merging.** In `layoutForRow`, after the main highlighter's spans for the line, each overlay's spans for that line are merged by `overlaySpans(base, overlay)` (`core/highlighter`): base spans are cut around the overlay's, the result stays sorted and non-overlapping, empty and `Default` spans of an overlay are skipped (they never erase the style underneath), later overlays win over earlier ones. With no overlays the editor does nothing extra.
- **Why a highlighter and not stored ranges.** Variable highlighting depends on state that is not in the text (which variables the request defines), is recomputed per visible line, and changes without any edit. A stored, anchored decoration would have the host rebuild and push every range on each change, and anchors for ranges that are rescanned anyway. An overlay computes what is on screen, costs nothing off screen, and invalidates exactly the lines it names. Hosts that do want anchored ranges still have decorations (ADR 0016); a `Style` decoration kind was left out because nothing needs it yet and it would duplicate this.
- **Bracket matching and search highlighting stay as they are.** They are frame-plan rectangles computed per frame from the cursor and the viewport; moving them to anchored ranges or to overlays would add work on every cursor move for no change in what is drawn.
- **Several independent sets** are several overlays (variables, search hits), each invalidating on its own.

## Consequences

- **Cost.** The merge costs 170 to 210 ns per laid-out line (40 base spans, 1 or 8 overlay spans; `benchmarks/results/2026-10-07-overlay-merge.json`, release build). Scrolling the 100 MB file with an overlay that styles every number, with a background (`...-overlay-scroll-*.json`, offscreen platform with the software backend: the display went away, so only CPU costs are comparable, not frame intervals): jumps (110 layouts a frame) polish 1.42 ms against 1.48 ms with the overlay (+4%, which includes the overlay's own scan), smooth 177 against 180 µs, cursor 159 against 158 µs, sync and render unchanged. Without overlays and without a background style the added work is a list-empty check and a flag test per layout.
- **Registration has no hot-path cost**, and style lookup in the theme is an array index.
- **Not done.** No unregister for languages or styles; no registration while parses run (see above); style slots are capped at 192; overlays are not offered to Markdown-style injections (an injected layer is the syntax highlighter's own); hands-on use inside Repose is checked with its tests only, not in a window.
