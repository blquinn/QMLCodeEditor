# 0011. Soft wrap: estimated row counts, refined on demand and in the background

- Status: Accepted
- Date: 2026-10-02

## Context

[ADR 0004](0004-display-map.md) fixed the layering (buffer lines, fold map, wrap map, display rows) and said that on resize the viewport is wrapped first and the rest in the background. M4 had to settle how that works for a 100 MB file with millions of lines, for a 5 MB line, and for rendering, which until now laid out one `QTextLayout` per buffer line ([ADR 0009](0009-rendering-pipeline.md)).

## Decision

- **Measuring lives behind an interface.** `core` has no fonts, so `WrapMeasure` (cell width, tab width, advance of a code point) is supplied by the host. `GridWrapMeasure` (one cell per code point, two for East Asian wide characters, none for combining marks) serves tests; the editor's `FontWrapMeasure` tabulates U+0000..U+00FF up front and measures other characters on first use with a mutex-guarded cache, because the background worker uses it too. Breaks come from summed advances. Rendering lays out exactly the text between two breaks, so a slightly wrong advance makes a row a little wider or narrower and can never make the two disagree about which characters are on a row.
- **A row is a column range of one buffer line.** `wrapRows()` breaks a line with a single forward scan: after whitespace when breaking at words (whitespace may hang past the right edge, and indentation is not a break opportunity), otherwise before the character that no longer fits. A row always holds at least one character cluster; surrogate pairs, combining marks, variation selectors, joiners and skin-tone modifiers stay with their base. The scan can stop after N rows and resume from the last break, which is what makes huge lines workable. Tabs advance to stops measured from the start of the row's text.
- **`WrapMap` is a blocked summary structure, not a persistent tree.** Row counts live in blocks of up to ~1000 lines (a `quint32` each, with a bit for "estimate"); three Fenwick trees over the blocks hold the sums of lines, rows and estimated lines. Line to row and row to line are one Fenwick descent plus a scan inside a block; an edit rewrites one or two blocks and rebuilds the Fenwick trees in O(blocks). That is O(log n) lookups with a small constant, and for 3M lines the whole map is about 12 MB.
- **Row counts are estimates until a line has been wrapped.** Turning wrap on, changing its width, or resetting the text marks every line as "one row, estimated" in O(lines) without reading the text. Queries (`rowAt`, `rowForPosition`, `rowCountOfLine`) wrap the lines they touch on the spot and so always answer exactly for what was asked; rows elsewhere may shift as their lines get wrapped, which `rowsReestimated` announces. A worker thread walks the estimated lines in chunks of about 1M UTF-16 units from a snapshot, and the GUI thread applies a chunk only if neither the text nor the config changed meanwhile (otherwise it is dropped and redone). `wrapProgress` and the editor's `wrapping` property say when everything is exact. `contentHeight` is therefore an estimate until then.
- **Edits re-wrap only the lines they touch,** up to a budget of 256K units. A big paste or a progressive file load beyond that leaves the new lines as estimates for the worker. `rowsChanged` is in row space.
- **Huge lines (over 64K units) are wrapped a few rows at a time.** Their break columns are kept (never evicted) and extended on demand, 64 rows ahead of what a query needs, and by the worker in steps of 4000 rows. Their row count is an estimate (`rows found + remaining units / row width`) until the scan reaches the end. An edit inside one keeps the breaks that start more than 1024 units before it. A jump to the end of a 5 MB line still scans all of it on the GUI thread (a few ms per MB in release).
- **Rendering is per row.** `LineLayoutCache` is keyed by (line, row in line); `CodeEditor::layoutForRow` lays out only the text of that row, slicing the highlighter's spans and the input-method composition to it. A 5 MB line therefore only ever lays out the rows in view. With wrap off a row is a whole line, exactly as before: the no-wrap path costs the same (`benchmarks/results/2026-10-02-scroll-after-wrap.json` against `2026-10-02-scroll.json`). This replaces the "a line is one `QTextLayout`" decision of ADR 0009 whenever wrap is on.
- **Positions at a soft break belong to the next row,** and `Selection` has no cursor affinity. A cursor therefore cannot rest after the last character of a row that continues; hit-testing and End stop one unit short (before the trailing space with word wrap). Home on a continuation row goes to the row start and a second press to the line's smart start; End goes to the row end, then the line end. Up/down use the goal X, which includes the hanging indent.
- **The view is anchored to text, not to a row number.** The editor remembers the buffer position (line, start column of the row) and pixel offset at the top of the view. When wrap settings change, the viewport width changes, or `rowsReestimated` fires, `contentY` is recomputed from that anchor. Anything that merely clamps `contentY` to a new content height must not overwrite the anchor.
- **Settings are applied once per frame.** The wrap properties and width changes only mark the wrap dirty; the next `updatePolish` applies the config, so a resize drag costs one reset per frame at most.
- **Wrapped text never scrolls sideways** with wrap-at-viewport (`contentWidth` equals the item width); wrap-at-column keeps horizontal scrolling when the column is wider than the item.
- **Hanging indent** is the line's leading whitespace (optionally plus extra columns), capped at half a row. Continuation rows are drawn that far to the right and are that much narrower.

## Consequences

- Scroll bar size and thumb position are approximate while `wrapping` is true. With 100 MB and 1.6M rows this lasts about 1 s after a toggle (`wrap/short_100MB/toggle_on_*/until_exact`), during which frames stay at the display rate.
- `DisplayRow::rowsInLine` is only exact once the line is exact; `isLast()` is always right for rows whose end is known.
- Per-row layouts mean a wrapped line costs one `highlightLines` call per visible row. Highlighters (M7) must make asking for one line repeatedly cheap, or cache per line.
- Tab stops restart at every row, so a tab at the start of a continuation row is not aligned with tabs on the first row unless the hanging indent is a multiple of the tab width.
- Gutters (M5) can tell first rows from continuation rows with `DisplayRow::isFirst()`; line numbers come from `DisplayRow::line`.
- Folding (M8) replaces `FoldMap`; the wrap layer already works in fold lines.
- Measured on a 100 MB, 2M-line file (release, Wayland): toggling wrap shows the first correct frame within two frames (11-14 ms), `polish` stays under 5 ms while the worker runs, and a resize sweep keeps 8.2 ms frame intervals. A 5 MB line wraps its first screen immediately; resizing while looking at its middle costs up to 20 ms per frame, because reaching the anchor means scanning from the start of the line. See `benchmarks/results/2026-10-02-wrap.json`.
